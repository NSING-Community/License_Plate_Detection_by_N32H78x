## 零、一句话

省份字（位置 0 的汉字）有**两个叠在一起的独立问题**，降门限只解决其中一个：

1. **检测**：它的框被 conf 门限删掉。位置 0 的 IoU≥0.5 召回在 conf 0.25 时只有
   **67.5%**，0.30 时 **51.8%**；放到 0.15 是 **96.5%**。少一个字符 → 逐位对齐整串错位 →
   后面 6 位全判错。这是**零重训**能修的。
2. **分类**：**框给真值也不行**。检测头在位置 0 的 argmax 只有 **28.79%** 正确
   （位置 4–6 是 85–89%）。同样的像素、同样的框，1,715,750 参数的探针头有 **96.69%**
   —— 所以这是**容量**问题，不是数据问题。**这个降门限救不回来**，要第二级识别头。

固件侧实测（`fw_emulate.py`，逐行复刻 `yolo_inference.cpp`）：

| | conf | NMS | 逐字 | 整串 |
|---|---|---|---|---|
| 现在是 | 0.25 | 0.45 | **54.31%** | **6.81%** |
| 调完（零重训） | 0.10 | 0.30 | **73.95%** | **12.06%** |
| 调完 + 续训检测器（ft119，见 §7） | 0.10 | 0.30 | **80.75%** | **27.04%** |

**+19.6 个逐字点、+5.3 个整串点，不重训、不加网络。** 但要越过 ~74% 必须加第二级。
（续训检测器是另一条 +6.8 逐字 / +15.0 整串 的路，**但它和下面那条路不叠加**，见 §3.5。）

⚠️ **上表的「现在」那一行是「裁剪版模型当一级」的口径（`fw_emulate.log`，默认 `--data data_crop/voc.data`），
不是当前部署的整图单模型固件。** 部署中的整图模型在固件口径下的真实水平见 §1.4 的订正表 ——
**逐字 28.30%、整串 0.00%**（voc-290 @ 0.25/0.45，`fw_current_firmware_voc290.log`）。
**这一行差别很大，别混口径引用。**（整篇其余「一级」列都是裁剪版口径，那是设计里的一级；

**不是 §2 那个容量问题被修好了** —— §2 里框给真值、检测头也只有 28.79%。）

第二级只花一级的 **31.7% 参数 / 22.6% 算力**（§9），把整串从 12.06% 拉到 **79.57%（×6.6）**，
并让**位置 0 追平其他位置**（92.41% vs 92.34%）—— 省份字这个坑填平了。
（\*那两列是**框召回**，不是字符正确率，两列口径不同，别横向比；见 §3.2。）

**这恰恰是两级结构最该被记住的性质：系统对检测器的依赖被第二级切断了。**
（它真正的价值是把 conf 敏感性拉平：0.10 和 0.15 从差 2.9 点变成打平 —— 见 §3.5。）

**还有一个硬顶要知道**（§3.6）：拼串长度完全等于留下的框数，514 张里只有 467 张
（**90.86%**）正好留 7 个框 —— 在这份数据上整串率不可能超过 90.86%。

⚠️ **换 ft119 之后这张表几乎没动**（正好留 7 个框的从 467 张变 **464 张**，
硬顶 90.86% → 90.27%）—— 这就是「端到端不吃检测器红利」的根因（§3.6）。

⚠️⚠️ **但这个 90.86% 是这份 val 的分布算出来的，不是场景的**（§3.8）：
val 是**连续切块**（不是随机划分），里面 **6 字牌占 3.5%、是 train 的 27 倍**，
而这 18 张的「6 字」其实是**真值少标了一个字**（例：`粤Z·C251澳` 被标成 6 字）。
**按 train 的串长分布重加权，整串是 84.02%（不是 80.93%）；
只用 7 字牌这一桶（= 98% 的部署场景）是 85.8%。**
而且**重心要改**：7 字桶里「长度对但字认错」是 **63 张**、
「长度错」只有 **6 张** —— **瓶颈是认字，不是数框**（§3.8 已推翻 §3.6 的旧重点）。

**🔥 那 63 张是谁、以及唯一的杠杆（§3.9，今晚最后一节，账已闭环）：**

| 环节 | 逐字 |
|---|---|
| 第二级识别头 @ **真值**字符框 | **99.08%**（数字 0–9 全 100%，33 个错几乎全是省份字） |
| 第二级识别头 @ **预测**字符框（真机链路） | **97.00%** |
| ⇒ 差值 = **框质量净代价 2.08 点**（折成 7 字整串 ≈ **8 个点**） | |

⇒ **完美定位下 7 字整串的硬顶 = `0.9908⁷` = 93.7%，现在 85.8% —— 中间 8 点全在框上。**
**识别头做完了**（top-3 只比 top-1 高 0.67 点，加语言模型没用）。

**坏框只有一个方向：太宽**（拆裂 0 个）。IoU<0.7 只占 **5.31%**，
但其中 **宽比 ≥1.3 的那 114 个字符（3.2%），二级逐字从 98.8% 崩到 59%**。
**和清晰度无关**（皮尔逊 0.012）、和 anchor 先验也无关（best-IoU 0.9025，是对的）。

**病根是网格分辨率**：320 空间里字符只有 **24px 宽**、间距 45.7px，
而 **stride-16 的格子是 16px —— 一个字符才 1.5 个格子宽**，
而 98.8% 的框都由这一层产出。
⇒ **唯一还没试过、也唯一有量级的杠杆：给字符加一个 stride-8（40×40）的头。**

**全链路今晚也串起来量过了**（§3.7，`full_pipeline_e2e.py`）：
整图找车牌（**plate AP ≈ 0.99**，实测检出 **496/514 = 96.5%**，车牌框 IoU 中位 0.892）
→ 外扩 10% 裁剪 → 裁剪版模型 → 第二级。
用最终检测器，**整串 78.02%**（砍到 7 个框 **78.99%**）；续训前是 76.26%/76.85%。

比从**裁好的图**起算的 79.96%（砍到 7 后 80.93%）低 **1.94 个点**，换算成张数就是 **10 张**
（402 − 392），而漏检是 **18 张** —— 同量级，且「18 张里 10 张在真值框下读得对」就完全解释掉。
⇒ **没有「可能变差」的未测环节了，代价全部来自那 3.5% 的车牌漏检。**

顺带测出一条**部署硬约束**：裁剪**必须**复刻 `make_plate_crops` 的「车牌框四周各外扩 10%」。
裁得**更紧**（字符更大）**反而掉 16.5 个点**（78.21% → 61.67%），裁松更惨（22.57%）——
因为裁剪版模型的 anchor 先验是配着那个取景训的。**这一条比看起来重要。**

**⚠️ 读法警告**：514 张验证集上 **1 张图 = 0.194 个点**。
所以 79.57 → 80.54 → 81.32 这些差（5~9 张图）**勉强算数**，
再往下的任何「0.2 个点」都不要当结论。**我没有另开测试集**，
上面的常数是在这份 val 上挑的 —— 换一份数据要重新确认，尤其是「砍到 7」和 NMS 0.20。

## 一、问题一：省份字的框被 conf 门限删掉

### 1.1 现象

串级错例压倒性的模式是**预测串少掉第一个字**：

```
京AEU669 | AEU669      冀JY1177 | J01177
黑MS1117 | MS1117      鄂ADS006 | ADS006
```

### 1.2 根因：分数低 —— 而且是 **cls_p 低，不是 obj 低**（订正）

按位置统计 IoU≥0.5 召回（`_diag_obj_vs_cls.py`，**不做 NMS**）:

| 位置 | conf≥0.30 | ≥0.25 | ≥0.20 | ≥0.15 | ≥0.10 |
|---|---|---|---|---|---|
| **0 省份字** | **51.75%** | **67.51%** | 85.21% | **96.50%** | **99.61%** |
| 1 | 96.69% | 97.86% | 99.03% | 99.22% | 99.61% |
| 2 | 94.55% | 96.69% | 98.44% | 99.61% | 99.61% |
| 3 | 95.91% | 98.44% | 99.22% | 99.42% | 99.42% |
| 4–6 | 98.4–98.8% | 98.8–99.4% | ~99.2% | ~99.4% | ~99.4% |

**conf 0.30 → 0.15，位置 0 从 51.75% 到 96.50%，其他位置一点没掉。**

**订正**：我先前写「检测头对省份字的 **objectness** 打分天生偏低一档」，**这是错的**。
把 `handel_preds` 的输出拆开看（`[:,4]`=obj、`[:,5:]`=softmax，`utils.py:433/436`），
在 IoU≥0.5 的框上按位置取中位：

| 位置 | 中位 obj | 中位 cls_p |
|---|---|---|
| 0 | **0.998** | **0.187** |
| 1 | 0.999 | 0.525 |
| 2 | 0.999 | 0.489 |
| 3 | 0.999 | 0.759 |
| 4 | 0.996 | 0.877 |
| 5 | 0.999 | 0.913 |
| 6 | 0.998 | 0.823 |

**obj 到处都饱和在 0.998–0.999，一格没差。** 低的全是 **cls_p（分类概率）**。
「obj 头饱和」这个说法在整图版上也成立：IoU≥0.5 的字符框里 **99.19%** 的 obj>0.30，
但 obj*cls>0.30 只有 **62.13%**。

**已排除「裁边切掉了」**：位置 0 的框左缘中位 0.22、宽高分布和其他位置一致
（`_check_first_char.py`，`pos0_vis.png` 可直接看）。
**已排除 class 0 抢框**：conf 0.02 全量扫 val，判成 class 0 的框**一个都没有**（0/0）——
`eval_plate.py --drop-plate` 实际上是空操作。

### 1.3 为什么一个字拖垮整串

逐位指标是「按 x 排序取前 `len(gt)` 个再逐位比」。
**少一个字 → 整串错位 → 后面 6 位全判错。**

这一条解决了一个一直对不上的数：`det@0.5` 有 90%，串级却只有一半。
但注意下一条 —— 光有框还不够。

### 1.4 整图模型也有，而且更糟

`_diag_obj_by_pos.py --data data/voc.data`：位置 0 中位 conf **0.185**（全位置最低），
conf 0.30 下召回 37.09%，放到 0.10 回到 94.37%。**所以不是裁剪版特有病。**

但整图版还有**门限救不回来的**部分——位置 3/4/5 即使 conf 放到 0.05，召回也只有
77.9% / 53.8% / 76.7%（位置 4 尤其差）。这是真正的定位失败。**这也是裁剪版作为一级更好的独立理由。**

⚠️ **下面这张表（`eval_full_conf.log`）是错的，2026-10-16 已订正。** 先给原表：

| conf | det@0.5 | ch% | 首字% | exact% |
|---|---|---|---|---|
| 0.30 | 61.31% | **23.68** | 18.83 | 0.00 |
| 0.20 | 73.07% | 22.30 | 22.33 | 0.19 |
| 0.10 | 82.67% | **15.08** | 25.24 | 0.00 |

当时据此写了「**整图版降门限会变差，单模型固件不能靠降门限救**」。**这个结论不成立。**

**错在哪**：`eval_full_conf.log` 是 `eval_plate.py` 的输出，而 `eval_plate.py:193` 调的是
`U.non_max_suppression` —— 仓库实现，**按类 NMS**（`utils/utils.py:376-379`：
`boxes = x[:,:4] + x[:,5:6]*max_wh`，不同类的框互不抑制）。
**固件不是这样**：`fw_nms()`（`fw_emulate.py:78`）是**类无关**贪心 NMS。
低 conf 下多出来的杂框在仓库版里因为「类不同」被放行，进了装配就变垃圾字符；
在固件版里它们会被同一位置的正确框按 IoU 压掉。**换错 NMS 才让降门限看起来有害。**

**固件口径重测（`fw_emulate.py --data data/voc.data`，521 张，与固件后处理逐行一致）：**

|---|---|---|
| 0.30 / 0.45 | 24.35% / 0.00% | 24.70% / 0.00% |
| 0.25 / 0.45 | 27.33% / 0.00% | 28.30% / 0.00% |
| 0.15 / 0.45 | 32.11% / 0.38% | 33.30% / 0.00% |

| 0.10 / 0.45 | 34.20% / 0.38% | 34.18% / 0.00% |

日志：`fw_current_firmware_voc299.log` / `fw_current_firmware_voc290.log`（geo off、maxbox 64 行）。

**门限越低越好，单调，和裁剪版同一个方向。** 从 0.25 放到 0.10：逐字 +8.79 / +9.20 点，
整串 0.00% → 0.96% / 0.00% → 0.77%（5 张 / 4 张图）。**所以「单模型固件不能靠降门限救」是错的 —— 能救 9 个逐字点。**
⚠️ 但**救不回量级**：整图单模型的整串率即便调到最优也只有 **约 1%**（5/521），
跟两级结构的 **78.99%** 差两个数量级。**§1.4 原来的定性判断（整图单模型不能用）是对的，
错的是它给的理由和「降门限有害」这条机制描述。**

（原因仍成立：整图模型 IoU≥0.5 的框里 argmax 类别正确的只有 **48.28%** ——
它认字本来就差，不只是框的问题。见 §二。）

## 二、问题二：**框给真值，检测头也认不对省份字**（今晚最重要的发现）

### 2.1 框准得很，字还是错

`_diag_obj_vs_cls.py` 绕开 NMS，对每个真值字符取**最佳 IoU 的 anchor**
（位置 0 的中位 IoU 是 **0.920**，和其他位置一样准），看 argmax 是不是真值类：

| 位置 | 中位 IoU | argmax 正确率 |
|---|---|---|
| **0 省份字** | 0.920 | **28.79%** |
| 1 | 0.919 | 60.62% |
| 2 | 0.921 | 67.12% |
| 3 | 0.917 | 79.73% |
| 4 | 0.914 | 88.67% |
| 5 | 0.917 | 88.50% |
| 6 | 0.924 | 85.69% |

**框是对的（IoU 0.92），字错了 71%。** 所以 §1 的「降门限」把框捞回来之后，
位置 0 的分类仍然只有 28.79%。

### 2.2 是容量，不是数据

`_probe_by_pos.py` 把**同一批像素、同一批真值框**喂给探针头
（`probe_charcls_32x64.pt`，**1,715,750** 参数，是检测器的 **7.1 倍**）：

| 位置 | 探针准确率 |
|---|---|
| **0** | **96.69%** |
| 1–6 | 99.03% ~ 100% |
| 全部 | 99.22% |

**同样的信息，换个头就从 28.79% 到 96.69%。**

### 2.3 也不是「数据不够」

`_count_cls.py` 数了训练集 4457 张 / 31281 个字符框的类别频次。
数字类每个约 1800 个；**省份类在位置 0 的样本量中位只有 111**：

| 最多 | 粤 476、鄂 360、吉 261、辽 261、赣 255 |
|---|---|
| …中位… | **111** |
| 最少 | 藏 9、宁 6、**新 5** |
| **一个都没有** | 澳、港、警、学 |

看着很像「样本少 → 学不会」。**但探针推翻了这个解释**：
把 val 里省份类按样本量分成两组（`_probe_by_pos.py`）—

| 组 | 类数 | 验证样本 | 认对率 |
|---|---|---|---|
| ≤30 个样本 | 31 类 | 483 | **96.1%** |
| >30 个样本 | 1 类 | 50 | 98.0% |

**2 个样本的类它也能认对。** 所以数据够用；
问题在 24.2 万参数的检测头里，35 类汉字要和 70 类检测 + 框回归**共用容量**，
位置 0 又只有中位 111 个样本，挤不出来。

> **但「数据不缺」有个限度，说清楚免得被读成「数据永远不用管」**：
> 探针自己的**最差 15 类全是省份汉字**（黑 85.0% n=20、京 87.0% n=23、
> 赣/晋/闽 90.5% n=21、警 92.3% n=13 …），而最好的 8 类全是很常见的字或字母。
> 也就是说：**把它做到 1.7M 参数，残余错误还是集中在那批小样本类上。**
> 正确的读法是「**容量是当前这个 24 万参数模型的第一约束，先动容量**；
> 等容量上去之后数据才会变成约束」—— 而不是「数据可以不管」。
> 真要补，得**用字体合成省份字**（省份字只在位置 0 出现，光多切字符样本没用）。

**抽样量对比更直观**（`_count_cls.py`）：数字/字母出现在**位置 ≥1** 时的样本量
中位 **415**、最少 135、最多 1987；省份字在位置 0 中位 **111**。
**同样的模型容量，数字类拿到的监督是汉字类的近 4 倍** —— 这也解释了为什么
位置 1–6 的 argmax 正确率（60–89%）远高于位置 0（28.79%）。

### 3.3 max_box=64 的核对（担心的坑，实测不成立）

`decode_head()` 的候选预算是**光栅顺序截断**，不是按分数：

```c
for (gy = 0; gy < gh && cnt < max_box; gy++)
  for (gx = 0; gx < gw && cnt < max_box; gx++)
    for (a = 0; a < 3; a++) {                    // 内层没有 cnt 检查
      if (obj*cls < YOLO_CONF_THRESH) continue;
      boxes[cnt++] = ...;
    }
```

两个 head 共用 `cnt`/`max_box`（`yolo_inference.cpp:3088` 同一次调用），main.c 传 **64**。
`_count_cand.py` 实测：conf 0.25 时候选数**中位 72**、**79.6%** 的图超 64；
conf 0.15 中位 87、98.6% 超。**我一度以为这会吃掉右下角的框、让降门限失效。**

**实测不成立**：NMS 收到 0.30 之后 64 和 1024 几乎一样（72.03 vs 71.45，73.95 vs 72.46）。
更奇怪的是 NMS 还是 0.45 时**调大 max_box 明显更差**（0.10/0.45：64→66.03，1024→51.10）
——候选一多，活过 NMS 的重复框就多，往串里插垃圾。**结论：别动 max_box。**

**这不是坏消息，这是两级结构最强的论据**：第二级存在的意义就是**把差框读对**，

**系统对检测器的依赖被这一层切断了**。
⇒ 结论没变：**别为了端到端去继续训检测器**（它的价值在单模型/低配路径、以及门限鲁棒性上）；
两级路径要涨，得修 §3.6 的「框数」（那是 NMS/后处理的事，不是训练的事）。

1. **最佳的固件常数组合没变，还是 conf 0.10 / NMS 0.30**（两张表都是这一行最好）。
2. **接上 16:32:64 这一档，整串 12.06% → 79.57%（×6.6）**，逐字 73.95% → 92.79%，
   位 0 从 **33.07% → 92.41%**。

   这是整篇报告的终点：位置 0 从 33.07% 到 92.41%，且和其他位置**追平**。
4. **第二级要多少参数，答案有了：~7.7 万，不是 2 万，也不是 170 万。**
   20,606 → 76,854（×3.7 参数）换来整串 65.76% → **79.57%（+13.8 点）**；
   而再往上堆到 1,715,750（**再 ×22 参数**）只到 81.32%（**+1.75 点**）。
   **76,854 参数已经拿到探针 98% 的整串率**（79.57 / 81.32）。
   ⇒ 推荐档是 **16:32:64**：×0.226 算力 / ×0.317 参数，int8 约 77 KB（§9）。
5. **⚠️ 整串率有一个 90.86% 的硬顶 —— 它由「框数」决定，不由分类头决定。
   这一条是我今晚先写错、又被数据纠正的，值得单独看（§3.6）。**
   拼出来的串有多长**完全等于留下的框数**，跟用哪个头无关。实测这 514 张里
   **467 张（90.86%）正好留下 7 个框**，其余 47 张长度就错了 ——
   **任何分类头都不可能在这 47 张上读对。** 所以：
   - 一级头 12.06% × 514 = 62 张全对
   - 8:16:32 → 338 张；**16:32:64 → 409 张**；探针 → 418 张

6. **第二级的收益远大于调常数。** 调常数把逐字从 54.31 抬到 73.95（+19.6、整串 +5.3）；
   接第二级再抬到 92.79（**逐字 +18.8，整串 +67.5**）——
   整串率才是「扫一次能读对几个车牌」的那个数。
7. **NMS 0.30 在两级下仍然是必须的**（0.10 时 0.45→0.30：整串 60.12% → 79.57%）。
   原因和第二级无关：多出来的框会被**插进 x 序**里，把整串挤错位。
   注意 0.10/0.45 那行，二级的位 0 有 92.80% 但整串只有 60.12% —— **错的是串的对齐，不是字。**
8. **一级那一列和 `fw_emulate` 逐位小数完全一致**（54.31/6.81、54.61/10.89、64.83/7.98、
   72.03/12.06、66.03/8.37、73.95/12.06），所以上面所有头的对照都是真·同框对照。

### 3.6 整串率的 90.86% 硬顶：剩下的错有一半是「框多了」

给 `two_stage_e2e.py` 加了 `--lendump`，把「预测串长度 − 真值串长度」的分布打出来
（`e2e_lendump.log`）。conf 0.10 / NMS 0.30：

| 长度差 | −3 | −2 | −1 | **0** | +1 | +2 | +3 |
|---|---|---|---|---|---|---|---|
| 张数 | 0 | 1 | 11 | **467** | 30 | 2 | 1 |

**这张表三个头完全一样**（一级/16:32:64/探针逐行相同）—— 因为**拼串长度 = 留下的框数**，
和分类头一点关系都没有。**结论：整串率对任何头都 ≤ 467/514 = 90.86%。**

拆开那 47 张：**33 张是框多了，12 张是框少了**（是 2.75 : 1，不是对称的）。
所以剩下的整串损失大致一分为二：

> ⚠️ **这一小节的「重心」后来被 §3.8 推翻了**：这里是在**全体 514 张平均**上看的，
> 被 6/8 字那几桶（真值少标字）的硬伤摊平了。**只看 7 字牌这一桶（98% 的部署场景），
> 「长度对但字错」63 张 vs「长度错」6 张 —— 识别误差是长度误差的 10 倍。**
> 而且 §3.6 那张 90.86% 硬顶是**这份 val 的串长分布**的产物，不是场景的。**先读 §3.8。**

- **47 张（9.1 个点）是框数错** —— 再好的分类头也救不了；
- **58 张（11.3 个点）是长度对但字错**（16:32:64）。探针是 49 张。
  两者只差 9 张 —— **头已经基本做完了。**

**⚠️ 换 ft119 检测器再 dump 一次，这张表几乎没动**（`e2e_lendump_ft119.log`）：

| 长度差 | −2 | −1 | **0** | +1 | +2 |
|---|---|---|---|---|---|
| ep90 | 1 | 11 | **467** | 30 | 2 |
| **ft119** | 1 | 14 | **464** | 28 | 4 |

**长度正确的反而少了 3 张（467 → 464），硬顶从 90.86% 掉到 90.27%。**
机制：ft119 定位更准 ⇒ 同一个字的重复框重叠更多 ⇒ **类无关 NMS 0.30 反而合并得更狠**，
「框多了」的从 33 张降到 32 张，但**「框少了」的从 12 张涨到 15 张**。
**一进一出，净持平。**

**这一张表就是「检测器白训了」的答案**：端到端的天花板是**框数**，不是检测精度；
ft119 把字认得更准（§3.2：33.07% → 49.61%），但**天花板本身没抬**，
所以接上第二级只剩 0.39 个点。**要抬天花板只能改「怎么数框」**（NMS / cap / 加一个长度分类），
**不是改「框有多准」。**
> ⚠️ **这句话当晚被 §3.9 收紧了**：「怎么数框」和「框有多准」**其实是同一个病**——
> 坏框全部是**太宽**（宽比 ≥1.3 就把字符吃掉），而「多一个框/少一个框」正是它的两端。
> 病根是**字符级定位的网格分辨率**（stride-16 的格子比字符还宽），
> 所以改 NMS/cap 这类解码规则只在少数几张上生效，**改定位头才有可能动那 63 张**。

**于是试了一个一行改动能救多少：NMS 之后按分数把框砍到 7 个**
（`--maxchars 7`；真车牌最多 8 字，训练集里 7 字 4366 张、8 字 84 张，所以 7 是合理常数）：

| conf / NMS | maxchars | 逐字 | **整串** | 位 0 | 位 1–6 |
|---|---|---|---|---|---|
| 0.10 / 0.30 | 关 | 92.79% | 79.57% | 92.41% | 92.34% |
| **0.10 / 0.30** | **7** | **93.96%** | **80.54%** | 91.63% | **93.80%** |
| 0.10 / 0.30 | 8 | 92.96% | 79.57% | 92.41% | 92.53% |
| 0.10 / 0.45 | 关 | 82.54% | 60.12% | 92.80% | 80.59% |
| 0.10 / 0.45 | 7 | 83.97% | 65.56% | **76.85%** | 84.75% |
| 0.15 / 0.30 | 7 | 91.54% | 77.63% | 88.91% | 90.94% |

**两条结论：**

1. **maxchars=7 能再拿 0.97 个整串点**（79.57% → 80.54%），长度正确的从 467 张涨到 482 张。
   **但它替不掉 NMS 0.30**（0.45 那两行：60.12% → 65.56%，还差得远）。
   **两个都做才对：conf 0.10 + NMS 0.30 + 砍到 7 个框 = 80.54%。**
2. **砍到 7 在 NMS 0.45 下会把位 0 打崩**（92.80% → **76.85%**）——
   因为 0.45 下一堆重复框，按分数取前 7 个会**把分数最低的省份字挤掉**。
   在 NMS 0.30 下重复框已经没了，砍的才是真误检，位 0 基本不掉（92.41 → 91.63）。
   **又一次说明 NMS 0.30 是前提，砍长度只是锦上添花。**
   （探针那一列也跟着涨：81.32% → **82.88%**。所以砍到 7 之后
   16:32:64 离探针还是 2.3 个点 —— **这个差距是两头一起动、消不掉的那个容量差**。）
3. ⚠️ 砍到 7 是**跟着数据集走**的（这份 val 里 98% 是 7 字牌）。
   换成绿牌（8 字）占比高的场景它**会变差** —— 上面 −1 那一格从 11 涨到 12
   就是唯一的 8 字牌被砍坏了。**稳健版本是砍到 8（这里不涨也不跌），
   或者由牌照类型决定砍到几。别把 7 当成普适常数。**
   反证很干脆：**砍到 6 会把整串打到 0.97%**（514 张里 98% 是 7 字牌），
   所以这一步不是「越紧越好」，是「要等于真实长度」。

**顺着这条线把 NMS 也往下扫了一遍**（都是 maxchars=7，conf 0.08/0.10 两列几乎完全相同，
说明这个平台不是 conf 挑出来的）：

| NMS | 0.30 | 0.25 | **0.22** | 0.20 | 0.18 | 0.15 |
|---|---|---|---|---|---|---|
| 整串 | 80.54% | 80.54% | **81.32%** | 81.13% | 81.13–81.32% | 81.32% |
| 位 0 | 91.63% | 92.22% | 92.41% | 92.80% | 93.00% | 93.39% |
| 位 1–6 | **93.80%** | 93.25% | 92.73% | 92.21% | 92.02% | **91.46%** |

**这是一个宽平台（0.15–0.22 之间都在 81.1–81.3%），不是一根尖峰** ——
5 个点的 NMS 区间只差 1 张图（1 张图 = 0.19 个点），所以这条曲线可信。
**而且它把 16:32:64 送到了 81.32%，正好等于 1.7M 探针在不加任何 cap 时的数。**
（⚠️ 这张表是 ep90 检测器的。**换 ft119 之后「位 0 涨 / 位 1–6 跌」这个换法消失了、
NMS 变成单调向好**，见 §3.7 那张对照表 —— 那是**全链路**（预测车牌框）口径，
真值框口径这里没有重扫。）

**但看位 1–6 那一行：NMS 越紧它越低（93.80 → 91.46），位 0 反而越高（91.63 → 93.39）。**
读法是：**收紧 NMS 在「合并掉相邻数字」和「删掉省份区的杂框」之间换**——
两头都在动，整串恰好抵消成平的。所以：
⇒ **可推荐的是「NMS 0.30 + 砍到 7 = 80.54%」**（位 1–6 还是最高的 93.80，机制最干净）；
NMS 再往 0.20 收能多 0.6 个点，但那是**拿相邻数字的命换的**，
**要在一份更大的验证集上确认了再改，别照着这 514 张调。**
（**噪声地板**：514 张 ⇒ **1 张图 = 0.194 个点**。所以下面所有「小于 0.5 个点」的差异
都不要当结论；`e2e_16_32_64.log`（79.57%）和这张表里的 81.32% 差了 9 张图，那个才算数。）

**我先前的一个推断，被这一档数据推翻了，写在这里因为它容易再犯**：
8:16:32（65.76%）离探针（81.32%）差 15.6 个整串点时，我判断「这是**容量差**，
所以下一步该加宽」。**方向对了，但量级我估反了** ——
我当时默认那段差距要按参数比例（×83）去填，实际上 **×3.7 就几乎填满了**（+13.8 点），
剩下 ×22 只值 1.75 点。**「容量不够」这个诊断对，不代表「要很多容量」也对。**
这两档的日志分别是 `e2e_two_stage.log`（20,606）和 `e2e_16_32_64.log`（76,854）。

### 3.7 真·全链路：整图 → 找车牌 → 裁剪 → 两级 —— **这一段补测完了**

§3.5 的每一个数字都是从 `data_crop` 的图开始算的，而**那些图是 `make_plate_crops.py`
用真值车牌框裁好的**。真机上第一级得自己找车牌。这一段一直是缺口，
所以今晚写了 `full_pipeline_e2e.py` 把它接上：**车牌框来自整图模型的预测**（`full_pipe_pred.log`）。

**先看第一级本身的质量**（`train_20261014b.log`、`eval_plate.log`）：

| 量 | 数 | 出处 |
|---|---|---|
| 整图模型 class 0 = **plate 的 AP** | **≈ 0.99**（末 6 次评估 0.992 / 0.999 / 1.001 / 0.996 / 1.000 / 0.997） | 逐类明细表 |
| 车牌框召回 @ conf 0.30 / NMS 0.45 | **97.49%**（505/518），base_0829 是 97.10% | `eval_plate.log` |
| 70 类**平均** AP | 0.2709 | 同上（**别拿这个数代表车牌**） |

⚠️ **两个读数陷阱，我都踩过**：
① 逐类明细表的列序是 `id name n_gt P R AP F1` —— **最后一列是 F1 不是 AP**。
车牌那一行是 `0 plate 518 0.62828 1.06371 0.99233 0.78996`，**AP 是 0.992，F1 才是 0.79**。
② 文件名里的 `voc-299-epoch-0.270855ap` 是 **70 类的算术平均**，被 35 个省份字/字母类拖得很低。
表中 `R` 还打印成 **>1.0**（1.06–1.07），是这套 AP 实现重复匹配的老毛病，
**P/R 那一对别单独引用**，要看召回率就用 `eval_plate.log` 的 97.49%。

**自对拍**：`full_pipeline_e2e.py --gt-plate`（车牌框用真值）就等价于重做一遍
`make_plate_crops` + §3.5，实测 一级 73.72%/12.26%、小头 92.34%/78.21%，
对上 §3.5 的 73.95%/12.06%、92.79%/79.57% —— 差的那一点是 `data_crop` 多了一道
**JPEG q95 存读**（我的裁剪是干净像素）。**对拍过了，下面的数才敢信。**

**真·全链路（预测车牌框，plate conf 0.25/NMS 0.45，conf 0.10/NMS 0.30）：**

| 车牌框来源 | 检出车牌 | 车牌框 IoU 中位 | 裁剪模型 | 小头 逐字 | 小头 **整串** | 砍到 7 个框 |
|---|---|---|---|---|---|---|
| 真值框（`--gt-plate`） | 514/514 | 1.000 | ep90 | 92.34% | **78.21%** | 78.99% |
| 真值框（= §3.5 那套 `data_crop` 图） | 514/514 | 1.000 | **ft119** | 91.91% | **79.96%** | **80.93%** |
| **整图模型预测** ← 真机 | **496/514（96.5%）** | **0.892** | ep90 | 92.14% | **76.26%** | 76.85% |
| **整图模型预测** ← 真机 | **496/514（96.5%）** | **0.892** | **ft119** | 91.52% | **78.02%** | **78.99%** |

**⇒ 「整图 → 裁剪」这一段值 −1.95 个整串点（换 ft119 之后 −1.94，几乎没变），比预想的小得多。**
把点换回张数：78.21% × 514 = **402 张**，76.26% × 514 = **392 张**，**差 10 张**；
而**漏检是 18 张**（496/514 = 96.5%）—— 同量级，且「18 张里只要有 10 张在真值框下能被读对」
就完全解释掉这个差（漏检的本来就是难例，10/18 = 56% 是很合理的比例）。
⇒ **裁剪框的偏移/松紧本身没有可测的代价**（IoU 中位 0.892 已经够）。

⚠️ **这里我上一版写错过一个对比**：原来写「在检出的 496 张上预测 79.2% vs 真值框 78.2%」——
那是**拿 /496 的数去比 /514 的数**，分母不同，不能这么比。
正确的同分母算法就是上面那 10 张的账；结论一样（代价可以忽略），但推理过程得对。

**换 ft119 之后这一段的收益反而更大**（76.26% → **78.02%**，砍到 7 后 76.85% → **78.99%**，
+1.8/+2.1 点，而不是 §3.5 真值框路径上的 +0.39）。
原因很直白：**真值框裁出来的图和训练分布一致，ep90 已经够用；
预测框有偏移（IoU 0.892），这才是需要「更会认字的模型」的地方** ——
所以同一个续训权重，在**离分布的输入上**比在干净输入上回报更大。
⇒ **要评一个模型值不值得换，得在真机那条链路上评，不能在理想输入上评。**

**降车牌门限救不回那 18 张**：plate conf 0.25/0.45 → 0.10/NMS 0.30，检出还是 496 张、
整串 76.46%（vs 76.26%）。**和 §1.4 同源：整图模型有些车牌是真的定位不到，不是门限问题。**
（要修只能重训整图检测器，那是另一件事。）

**⚠️ 但有一个部署约束必须写死：裁剪必须复刻 `margin = 0.10`。**
用真值框把 margin 扫一遍（`--gt-plate`，只变裁剪松紧；下面这组用 ep90 裁剪模型，
但差的是 16 个点量级，**换权重摇不动它**）：

| margin | 小头 逐字 | 小头 **整串** | 位 0 | 位 1–6 |
|---|---|---|---|---|
| 0.00（最紧，字符最大） | 80.47% | **61.67%** | 90.47% | 78.51% |
| **0.10（`data_crop` 就是这样裁的）** | **92.34%** | **78.21%** | 92.02% | 91.85% |
| 0.30（松） | 63.09% | **22.57%** | 73.35% | 56.73% |

**裁得比训练时更紧反而更差 16.5 个点** —— 我原来猜「字符更大 ⇒ 更好」，**猜错了**。
原因是裁剪版模型和它的 anchor 都是在 margin 0.10 的框上训的：
换个取景，字符尺寸和锚框先验就对不上（框/图也从 6.99 变成 7.30，多出来的是错框）。
⇒ **margin 0.10 是模型契约的一部分，不是可选的美化**；
真机裁剪必须按「车牌框四周各外扩 10%」来，而且车牌框要准到 **IoU ≈ 0.9**（现有检测器中位 0.892，正好够）。

**NMS 再往紧收，和 §3.6 是同一张图**（全链路、conf 0.10、cap 7；`full_pipe_nms.log`）：

| NMS | 0.30 | 0.25 | 0.22 | 0.20 |
|---|---|---|---|---|
| ep90 | 76.85% | 77.82% | 78.21% | — |
| **ft119** | 78.99% | 79.57% | 79.96% | **80.35%** |

而且 **NMS 收紧之后「砍到 7」就不再加分了**（ft119、0.22 下 79.77 → 79.96 只多 1 张；0.20 下两者都是 80.35%）——
两个机制本来就在修同一件事（多出来的框）。

⚠️ **一个和 §3.6 不一样的地方**：ep90 时收紧 NMS 是**位 0 涨、位 1–6 跌**的两头换；
**换 ft119 之后这个换法消失了** —— 0.30 → 0.20 时位 0 从 88.72 → 89.69、
位 1–6 也从 87.50 → 88.41，**两边一起涨**（§3.6 里 16:32:64 在真值框路径上还是「换」）。
⇒ 说明**检测器够好之后，「合并相邻数字」的损失被压下去了**，
NMS 收紧就只剩下「删杂框」这一个好处。

**但推荐档仍然保留在 NMS 0.30 + 砍到 7 = 78.99%**：0.20 那 1.36 点（7 张）是在**同一份
514 张 val 上挑出来的**，§3.6 和 §8 都标了「要更大的验证集才能改」。
**如果现场只有固定安装角度（分布稳定），可以大胆收到 0.20，这里的证据是单调向好的**；
**要跨场景部署就先用 0.30。**

**所以全链路诚实的落地数字是：整串 78.02%（砍到 7 个框 78.99%）** ——
用最终检测器（`voc_crop_ft-119`），而不是 §3.5 从裁好的图起算的 79.96%/80.93%。
（续训前是 76.26%/76.85%。）
**到这里就没有「可能变差」的未测环节了** —— 唯一的损失是 **3.5% 的车牌漏检**，
且那 18 张是整图检测器的定位失败（降门限救不回），**换裁剪模型也摇不动它**（gap 恒为 ~1.95 点）。

### 3.8 ⚠️ 验证集本身有分布偏 —— **报出来的 80.93% 低估了约 3 个点**

补「独立验证」的时候先查了一件事：**这 514 张是怎么划出来的**。答案是
**按文件名排序后连续切块**（train = `0000–4458`，val = `4459–4979`），
**不是随机划分**。而 `datasets/`（28 张）和 `img/`（34 张）只是演示集 ——
**整个数据集 4980 张全在 train+val 里，没有未用过的池子**。
所以「独立测试集」这条路不存在；能做的是**把常数选择和大家报告的那份数据分开**（见下）。

先看这块「连续尾块」代表不代表整体（`_split_compare.py`，只读 label，秒级）：

| 每图字符数 | train (4457) | **val (514)** |
|---|---|---|
| **6 字** | 6 张（**0.13%**） | **18 张（3.50%）** |
| 7 字 | 4366（97.96%） | 485（94.36%） |
| 8 字 | 84（1.88%） | 9（1.75%） |

**val 里 6 字牌的占比是 train 的 27 倍。** 而且这 18 张**聚在一起**
（`4770,4771,4774,4776,4777,4778,4779,4780` 连续 8 张）——
典型的「同一批采集」痕迹，这正是连续切块的代价。

**这 18 张是什么？** 往 `two_stage_e2e.py --lendump` 里加了「真值串长 × 预测串长」交叉表
（`e2e_crosslen_ft119.log`，conf 0.10 / NMS 0.30）：

| 真值 \ 预测 | 6 | 7 | 8 | 9 | 10 | 合计 |
|---|---|---|---|---|---|---|
| **6 字** | **0** | 15 | 1 | 0 | 2 | **18** |
| 7 字 | 6 | **463** | 13 | 3 | 0 | 485 |
| 8 字 | 0 | 8 | 1 | 0 | 0 | 9 |

**18 张 6 字牌里，预测出 6 个框的是 0 张 —— 一张都没有**
（不砍时也是 0/18）。**看图才发现原因：这些「6 字」是标注/裁剪伪影，车牌上本来就有第 7 个字。**
例：
- `4770/4771` 是**粤式两地牌**「**粤Z·C251 澳**」——真值串只有 `粤ZC251`（6 字），
  **末尾那个「澳」没被标进去**；
- `4554` 是张糊掉的黄牌，label 是 `DH9859`，但图里 D 前面还有一个字符没标。
⇒ **这 18 张是「真值少了一个字」，模型多输出的那个框是对的。**
**它们对任何模型都是零希望，却按 3.5% 的占比把整串率往下拽。**

**按真值串长分桶，代表性数字就出来了**（cap 7）：

| 真值串长 | 张数 | 长度对上 | **整串** |
|---|---|---|---|
| 6 字 | 18 | 0.0% | **0.0%**（0/18） |
| **7 字 ← 部署主体** | **485** | **98.8%** | **85.8%**（416/485） |
| 8 字 | 9 | 0.0% | 0.0%（0/9） |
| 9 / 11 字 | 2 | 0.0% | 0.0% |

**按 train 的串长分布重加权 ⇒ 整串 84.02%**（val 原始 80.93%；不砍时 83.01% vs 79.96%）。
⇒ **报出去的 80.93% 被 val 的分布偏低估了约 3 个点**，
**对部署有意义的那个数是 7 字桶的 85.8%。**

**⚠️ 这一节还推翻了 §3.6 的重心。** §3.6 说「剩下的错一半是框多了」——
但那是在**全体平均**上看的，被 6/8 字那几桶的硬伤摊平了。**只看 7 字这一桶（98% 的部署场景）：**

| 7 字桶（485 张，cap 7） | 张数 |
|---|---|
| 长度就对不上 | **6** |
| 长度对、**字认错** | **63** |
| 合计读对 | 416 |

**识别误差是长度误差的 10 倍以上（63 : 6）。**
⇒ **§3.6 那句「要抬天花板只能改怎么数框」对全体平均成立，对真实场景不成立** ——
**在 7 字牌上，瓶颈是「字读错」，不是「框数」。**
（§3.6 那条 90.86% 的硬顶同理：它是**这份 val 的串长分布**算出来的，
按 train 分布重算，7 字桶的**长度上界是 98.8%**，不是 90.86%。）

⚠️ **但这 63 张也救不回来**：1,715,750 参数的探针头在这同一批框上只多拿 10 张（§3.6），
所以**不是解码容量**。往「框更准」（字符级定位）或「图更清楚」上找，
不是往「分类头更大」上找 —— 这条和 §4 的结论一致，只是现在知道它**主要发生在 7 字牌上**。

### 3.9 那 63 张到底是什么 —— **账闭环了：全部是「框太宽」，而定位头已经没余量了**

§3.8 说「7 字牌的瓶颈是字读错」，§3.7 说「换更好的头只值 1.76 点」。两条合起来
只说明**不是头**，没说清**是什么**。这一节把它查完了，用的三个脚本都是新写的、
总共跑不到一分钟（都只读 label + 跑一次裁剪模型前向）。

**第一步：把识别头单独拎出来，喂真值字符框（`_char_confusion.py`）。**

| 口径 | 读对 |
|---|---|
| 二级头 @ **真值**字符框，3595 个字符 | **99.08%**（3562 对 / 33 错） |
| top-2 / top-3 / top-5 | 99.61% / 99.75% / 99.81% |

**数字 0–9 是 100%（1、2、3、5、6、9 全对），大部分字母也是 100%。**
那 33 个错**几乎全是省份字**：京→琼(3)、宁→吉(2)、藏→贵(2)、鄂→贵、黑→川、晋→黑、
晋→甘、沪→P、津→苏、闽→湘、甘→桂、陕→皖、豫→桂；
字母里只有 M→N、M→H、V→W、U→J、Q→粤、Y→1 各一次。

⇒ **识别头做完了，而且 top-3 只比 top-1 高 0.67 点 —— 加语言模型/重排序最多捞回这 0.67 点。**
`99.08%` 逐字 ⇒ 完美定位下的整串硬顶 = `0.9908⁷` = **93.7%**。
**这就是 7 字牌的天花板，而且它离现在的 85.8% 不远 —— 中间那 8 个点全在框上。**

**第二步：同一批框，把识别头从真值框换到预测框（`_char_box_quality.py`）。**

| 喂给二级头的是 | 逐字 |
|---|---|
| 真值字符框（完美定位） | **99.08%** |
| **检测器预测的字符框（真机链路）** | **97.00%** |

⇒ **框质量净代价 = 2.08 个逐字点**，折成整串约 **8 个点**（85.8% → ~93.7%）。
**闭环：85.8% 的账 = 93.7%（完美框的顶）− 8 点（框的代价）**，和实测吻合。

按 IoU 分桶看得更细（同一个识别头，只是框不同）：

| 最佳预测框 IoU | 字符数 | 占比 | 二级逐字 |
|---|---|---|---|
| 0.0–0.30 | 11 | 0.3% | 9.1% |
| 0.3–0.50 | 58 | 1.6% | 37.9% |
| 0.5–0.70 | 122 | 3.4% | 73.8% |
| 0.7–0.80 | 269 | 7.5% | **97.0%** |
| 0.8–1.01 | 3135 | 87.2% | **99.3%** |

**IoU ≥ 0.7 就掉不动了（97~99%）**；IoU<0.7 的只占 **5.31%**，但逐字率跌到 9–74%。

**第三步：坏框是「怎么坏」的。**

| 坏法 | 个数 | 占坏框 | 占全体 |
|---|---|---|---|
| **合并**（宽比 ≥1.5，中心基本重合） | 59 | 30.9% | 1.64% |
| **拆裂**（宽比 ≤0.67） | **0** | **0.0%** | **0.00%** |
| 漂移（中心偏 ≥0.5×GT 宽） | 17 | 8.9% | 0.47% |
| 其他（尺寸也怪） | 115 | 60.2% | 3.20% |

宽比（预测框宽 ÷ 真值框宽）在坏框里：`p25 1.14  p50 1.33  p75 1.62  p90 1.81`。
**一个拆裂都没有 —— 坏框只有一个方向：太宽。**

按宽比看二级头逐字率，**分界线极陡**：

| 宽比 | 字符数 | 二级逐字 |
|---|---|---|
| 0.9–1.1（宽度对） | 3018 | **98.84%** |
| 1.1–1.3（略宽） | 344 | 95.06% |
| **≥1.3（太宽）** | **114** | **59.0% / 45.3%** |

⇒ **114 个字符（3.2%）的框宽到真值的 1.3 倍以上，它们的逐字率从 98.8% 崩到 59%（宽比>1.6 时只剩 45%）。**
一个 7 字牌只要有 1 个字符落进这一档，整串就废 —— `1 − 0.032 ≈ 0.968`，
`0.968⁷ = 80%`，和实测的 85.8% 是同一个量级。**这就是那 63 张的身份。**

**第四步：排除「这是糊图/小图造成的」（否则改架构没用）。**

| 清晰度（Laplacian 方差） | 字符数 | IoU<0.7 | 二级逐字 |
|---|---|---|---|
| 最糊的 1/5 | 725 | 3.59% | 97.2% |
| 中间 1/5 | 728 | **8.93%** | 94.6% |
| 最清的 1/5 | 720 | 4.17% | 98.3% |

**皮尔逊(清晰度, IoU) = 0.012 —— 和糊不糊基本无关。**
裁剪图宽度也一样（最窄档 5.4% 坏框，最宽档 8.1%，最大也才 8%）。
⇒ **坏框不是光学/数据问题，是模型侧的，可以改。**

**第五步：坏框是哪个 stride 的头产出的。**

| 来自哪一层 | 选中框数 | 占比 | 其中 IoU<0.7 |
|---|---|---|---|
| 层 0（20×20，stride 16） | 3553 | **98.8%** | **5.0%** |
| 层 1（10×10，stride 32） | 42 | 1.2% | 33.3% |

**98.8% 的字符框由 stride-16 那层给出，坏框也几乎全在它身上。**

**机制（这一步是关键）**：在 320×320 的网络输入空间里，一个字符框是
**约 24px 宽 × 74px 高**（中国车牌字符 45×90mm，本来就是 1:2），
**字符间距（pitch）约 45.7px**。而 stride-16 的格子是 **16px** ——
⇒ **一个字符只有 1.5 个格子宽**；相邻两个字符的中心才隔 2.9 个格子，
两个框之间的空隙只有 1.36 个格子。
**这个尺度上，网络要把相邻字符分成两个框、还要把宽度回归准，是先验上就很难的事。**

⚠️ **不是 anchor 先验的问题**（这是我一开始怀疑的）：`_anchor_check.py` 直接算了
`data_crop/anchors6.txt` 和真值框的最佳 IoU（中心对齐）= **均值 0.9025**，
6 个 anchor 长宽比 0.12–0.33，和真值框的 0.30 对得上。
**anchor 是对的，格子太粗。** 宽度参数化 `(2σ)²×anchor` ∈ (0, 4] 也够表达合并框，
所以也不是解码被截断。

**⇒ 结论：剩下的唯一杠杆是「给字符更细的网格」，即加一个 stride-8（40×40）的头。**
字符会从 1.5 个格子变成 **3 个格子**，相邻字符空隙从 1.36 格变成 2.7 格。
按 §3.9 第二步的量级，**最好的情形是拿回那 8 个整串点（85.8% → ~93.7%）**，
现实一点是修掉 5.3% 坏框里的大部分 ⇒ 5–8 点。

**这个结论把 §3.6 彻底换掉了**：§3.6 说瓶颈在「怎么数框」（要改拼串逻辑），
现在看清楚了 —— **「框多一个/少一个」和「框太宽把两个字吃进去」是同一个病**，
病根是**字符级定位的分辨率**，不是拼串规则。改解码逻辑（maxchars、NMS 调参）
只在 6 张图上生效，改定位头才有可能动那 63 张。

### 6.1 ✅ 猜测被证实了 —— 而且多了一位

**三条都值得单独说：**

1. **位置 0（省份字）10.7% —— 我猜对了。** 而且「固定错 2 位 ⇒ 1-CER = 5/7 = 71.4%」

### 6.2 这张表独立验证了整篇报告的核心论断

把三级结构的同一个位置摆在一起（都在 val 上）：

| 方法 | 看到字符的分辨率 | 位 0（省份字） | 数字位 |
|---|---|---|---|
| **CTC 单阶段** | 整图 96×160，每个字约 **13px** | **10.7%** | **91–93%** |
| 两级（裁剪+放大） | 每个字重采样到 **32×64** | **92.41%** | **92.34%** |

**这是对「13px 字符装不下省份字」这个论断最干净的一次对照实验**：
同一个数据集、同一个任务，单阶段模型在数字位上已经做到 **91–93%**，
**和两级结构（92.34%）打平**；可它一碰到省份字就掉到 10.7%（两级是 92.41%）。
⇒ **数字这个任务在 13px 下本来就够，省份字不够** —— 差的正是
「字符笔画复杂度 × 像素数」这一项，而裁剪 + 放大直接把它补上了。
**这也解释了为什么位置 1（字母）在 CTC 里也塌**：字母笔画比数字复杂，
13px 处在临界线上；两级放大后有 98.83%（真值框口径）。

**⚠️ 一个必须说清的口径差别**：CTC 的位置 1 是「第一个字母」，两级的「位 1–6」
是把字母和数字合在一起平均的。所以上面这张表**位 0 那一列可以直接比，
「数字位」那一列是近似比**（CTC 的 2–6 纯数字 vs 两级的 1–6 混合）。

### 6.3 那还要不要继续跑 CTC？

**要，但理由变了。** 原来 §8 第 5 条把 CTC 降级为「有空再跑完」，理由是「落后太多」。
**它确实还落后（整串 0.58% vs 79.57%），但现在它的价值不在那个数**：
它是**唯一一个能在单阶段下把「分辨率瓶颈」单独暴露出来的对照**，
而且它已经给出了答案。所以：

- **不要**指望它靠多跑 50 轮追上来（1-CER 从 72.32% 爬到 72.88% 已经基本不动了，
  瓶颈是位置 0/1 认不出来，不是训练不够）。
- **值得**让它跑完，作为「单阶段方案打不过两级」的**书面证据**留档。
- **每轮存最好权重**已经开了，所以跑多久都不浪费。

## 八、建议（按性价比）

1. **固件改常数（零重训、零新网络、零额外内存）**：
   conf `YOLO_CONF_THRESH` **0.25 → 0.10**，并且**二选一**：
   - NMS `YOLO_NMS_THRESH` **0.45 → 0.30**，或
   - 把已有的 `plate_geo_filter()` 打开（'v' 键，代码在，默认关）。

   **两条必须一起改**，只降 conf 会更差。实测逐字 **54.31% → 73.95%**、整串 6.81% → 12.06%。
   `max_box=64` **不用动**（§3.3 实测）。
   **可选再加一条**：NMS 之后按分数把留下的框砍到 7 个（§3.6）—— 单看这一条
   整串 **79.57% → 80.54%**。但它**替不掉** NMS 0.30（0.45 下整串只有 65.56%），
   且「砍到 7」是跟着数据集走的（这份 val 98% 是 7 字牌），
   **绿牌多的场景要砍到 8**。所以它是锦上添花，不是必需。
   （**再往下 NMS 收到 0.20 能到 81.32%**，但那是拿相邻数字的准确率换的
   —— 位 1–6 从 93.80% 掉到 92.21%，**要先在更大的验证集上确认再改**。§3.6。
   **不过换 ft119 检测器之后这个换法在全链路上消失了**：0.30 → 0.20 时位 0 和位 1–6
   **一起涨**，整串 78.99% → 80.35%（§3.7）。**所以「收到 0.20」的代价可能被高估了** ——
   仍然建议先在更大验证集上确认，但它现在看起来是安全的。）
   ⚠️ **这里所有的点差都建立在 514 张 val 上（1 张 = 0.19 点），96% 的提法都不该被过度解读。**
   ⚠️ 但**别把这个结论套到当前的单模型整图固件上** —— 单模型整图版即便把门限调到最优，
   整串也只有 **约 1%**（§1.4 固件口径重测：0.10/0.30 → 逐字 36~38% / 整串 0.77~0.96%）。
   **「降门限」对整图版同样是往好的方向，但它救不回量级 —— 差距是两级的结构差，不是门限差。**

2. **加第二级字符识别头 —— 这是收益最大的一步，而且已经端到端验证过了。
   要加的档是 16:32:64（76,854 参数），不是最省的那档。**
   §3.5 实测（同一批真预测框、真固件后处理、val 514 张全量）：
   **16:32:64 的字符头**（一级的 31.7% 参数 / 22.6% 算力）把
   **整串从 12.06% 拉到 79.57%（×6.6）**、逐字 73.95% → 92.79%、
   位置 0 从 33.07% → **92.41%**（并追平位 1–6 的 92.34%）。
   （**79.57% 是「车牌已经裁好」起算的**；从整图起算的诚实数字是 **78.02%**，见 §3.7 ——
   差的 ~1.9 点是 3.5% 的车牌漏检，**不是第二级的问题**。）
   更省的 8:16:32（20,606 参数 / 5.9% 算力）也能到 65.76% / 83.85%，
   **预算实在紧就退到这一档，够用**；但 16:32:64 只多花 3.7 倍参数就多拿 13.8 个整串点，
   性价比明显更好。
   旁证两条：同样的**预测框**上，识别头 91.4% vs 检测头 73.4%；
   同样的**真值框**上，99.2%（探针）/ 98.9%（16:32:64）vs 检测头 71.2%（§2.1、§2.4）。
   探针那 1,715,750 参数只是用来证明「信息在像素里」，**不用部署** ——
   而且 16:32:64 已经拿到它 98% 的整串率（79.57 / 81.32），
   剩下的 1.75 个点是 22 倍参数换来的，不值得。
   **⚠️ 但别把 90.86% 当起点，也别把这 79.57% 当成「头还不够好」**：
   那一节（§3.6）的 90.86% 是**这份 val 的串长分布**算出来的，按 train 分布重算
   7 字桶的长度上界是 **98.8%**（§3.8）；真正压在头上的是**字符框的定位精度**。
   **§3.9 已闭环**：同一个头，喂真值框 **99.08%** 逐字，喂预测框 **97.00%** ——
   **框吃掉 2.08 个逐字点 ≈ 8 个整串点**，7 字牌完美定位的硬顶是 **93.7%**。
   **加宽分类头一点用没有**（1.7M 探针在这批框上只多 10 张），
   剩下那 8 个点只有一条路 —— 见下面第 4 条。

3. **⚠️ 先确认 MCU 的算力/内存预算能不能装第二级。** 两级 = 两个网络。
   **算力和参数都不是障碍**：§9 实测，16:32:64 也只要一级的 **22.6% 算力 / 31.7% 参数**
   （76,854 参数，int8 约 77 KB），它在真值框上位置 0 已经拿到 **95.14%**
   （一级头只有 28.79%；探针 96.69%）。要更省就用 8:16:32（5.9% 算力 / 8.5% 参数）。
   另外裁剪版模型的 class 0 头**没训过**（数据集里没有车牌框），**它不能定位整图里的车牌** ——
   两级要跑的是「整图模型找车牌 → 抠出来 → 裁剪版模型认字」。
   **第一级本身不用再训了**：整图模型的 plate AP ≈ **0.99**、实测检出 **96.5%**（§3.7），
   它是全链路里最好的一环。**全链路实测整串 78.02%**（砍到 7 个框 78.99%，§3.7）——
   比从裁好的图起算的 79.96% 低 ~1.9 点，**而这 ~1.9 点（10 张）就是那 3.5% 漏检的车牌**。
   ⚠️ **实现时必须复刻「车牌框外扩 10%」再裁**（§3.7）：裁更紧掉 16.5 点、裁松掉 55 点，
   **因为裁剪版模型的 anchor 先验是配着那个取景训的**。这是全篇最容易被忽略的一条部署约束。

4. **续训裁剪版：已跑完，换它，但别指望它救端到端**（§7）。
   `voc_crop_ft-119-epoch-0.589619ap-model.pth`，AP **0.4770 → 0.5896（+24%）**，
   ft60 就收敛了（后 60 轮晃在 0.583–0.590）。
   **在两条路径上回报完全不同，这是今晚第二个反直觉的结果**：
   - **单模型 / 低配路径：大涨** —— 固件口径逐字 73.95% → **80.75%**、
     整串 12.06% → **27.04%**（翻倍多）；换头对照里的位置 0 从 33.07% → 49.61%。
   - **两级 / 端到端路径：几乎不动** —— §3.5 上 +0.39 点（79.57% → 79.96%），
     **因为天花板不在检测头的精度，而在字符框的位置分辨率**（§3.6 当时说的
     「在框数」是同一件事的早期说法，§3.9 已经把它精确到「框太宽」）。
     ⚠️ 但**真机那条链路（§3.7）上它值 +1.8 点**（76.26% → 78.02%）——
     预测框有偏移，正是它发挥的地方。**所以「值不值得换」要在真机链路上评。**
   ⇒ **换，停掉继续训**（已经收敛）；**但别再指望训检测器能抬两级结构的天花板。**

5. **CTC 线（单阶段）—— 不要投产，但它现在是整个方案的对照组，价值反而上升了**（§6）。
   解码 bug 已修好、确实在学，**它现在落后太多**（ep10 整串 0.19%，两级是 79.57%，
   差 400 倍），这个数**不靠多跑 50 轮能补**：ep7→ep8 的 1-CER 只从 72.21% 爬到 72.88%，
   已经平了。**但 ep8 的逐位置读数给出了本轮最有价值的一个对照**：
   - 单阶段在**数字位**上做到 **91–93%**，和两级结构的 92.34% **打平**；
   - 可它在**省份字**上只有 **10.7%**（两级是 92.41%），**第一个字母**只有 **16.9%**。
   ⇒ 同一个数据集、同一个任务，**唯一变量是「每个字占多少像素」**：
   单阶段整图 96×160 下一个字约 13px，两级裁剪后重采样到 32×64。
   **这就是「13px 装不下省份字」这句话最直接的实验证据。**
   所以：**投产走两级**；CTC 保留为「单阶段为什么不行」的书面证据，
   让它跑完（每轮存最好权重，跑多久都不浪费）。
   （另：它每轮约 430–520 秒，60 轮再过 6 小时也跑不完，明早大概到 ep20 一线。）

6. **🔥 唯一还没试过、也是唯一还剩量级的杠杆：给字符加一个 stride-8 的头**（§3.9）。
   **为什么是它**：§3.9 把账闭环了 —— 识别头在真值框上 **99.08%**（数字全对、
   33 个错几乎全是省份字、top-3 只高 0.67 点），在预测框上是 **97.00%**。
   **差的 2.08 个逐字点（≈8 个整串点）全在字符框上**，而坏框只有一个方向：**太宽**
   （拆裂 0 个；宽比 ≥1.3 的 114 个字符，二级逐字从 98.8% 崩到 59%）。
   **和图像清晰度无关**（皮尔逊 0.012），**和 anchor 先验也无关**（best-IoU 0.9025）。
   **机制**：320 空间里字符 **24px 宽 / pitch 45.7px**，而 **stride-16 的格子是 16px
   —— 一个字符只有 1.5 个格子宽**，且 **98.8% 的框由这一层产出**。
   **改法**：在裁剪版检测器上加一个 40×40 的 stride-8 头（YOLOv5 的 P3 位置），
   anchor 用 `genanchors.py` 在 `data_crop` 上重聚一次（字符会从 1.5 格变成 3 格）。
   **收益量级**：最好的情形是拿回那 8 个点（85.8% → ~93.7%，
   因为 93.7% 就是「框全对」时这个头的硬顶）；现实一点是 5–8 点。
   **代价**：一级参数/算力会涨（多一层 P3），要重新量 §9 那张表；
   固件解码器要多扫一层（`fw_decode` / `decode_head()` 的层数从 2 变 3）。
   **⚠️ 但这是全篇唯一一条「还没被实测过」的建议** ——
   §3.9 只证明了「瓶颈在定位分辨率」，没证明「加一层就能修」。
   **所以第一步应该是先训这个新头、在同一批图上量 §3.9 的第 5 项**
   （真值框 99.08% vs 预测框 —— 现在是 97.00%），**这个数涨了才继续往下走。**
   **⚠️ 不要在拿到这个数之前动固件解码器。**

## 九、算力 / 存储预算（为「第二级装不装得下」量）

`_flops.py`。MACs 用 forward hook 数 Conv2d + Linear（ReLU/BN/池化忽略），
MFLOPs 按 1 MAC = 2 FLOPs。第二级输入的字符条统一重采样到 **32×64**。

| 模型 | 参数 | MACs | MFLOPs/帧 | 相对算力 | 相对参数 |
|---|---|---|---|---|---|
| **一级检测器 @320×320** | **242,365** | 87,559,200 | 175.12 | 1.000 | 1.000 |
| 第二级 SmallCharNet **8:16:32** | **20,606** | 5,163,200 | 10.33 | **×0.059** | ×0.085 |
| 第二级 SmallCharNet 16:32:64 | 76,854 | 19,763,584 | 39.53 | ×0.226 | ×0.317 |
| 第二级 SmallCharNet 32:64:128 | 296,486 | 77,275,904 | 154.55 | ×0.883 | ×1.223 |
| 探针 CharCNN（**参照，不是候选**） | 1,715,750 | 106,120,704 | 212.24 | ×1.212 | ×7.079 |

**结论：第二级不是「装不装得下」的问题。** 推荐档（16:32:64）只要
**22.6% 的额外算力、31.7% 的额外参数**（int8 约 77 KB），而它在真值框上
位置 0 已拿到 **95.14%**、整串 98.89%（一级头 28.79%）。
每帧总成本从 175 → 215 MFLOPs（**+22.6%**）—— 对一颗跑得动一级的 MCU 来说不算什么。

### 顺带订正一个一直被引用的数字

训练日志里的 `Total params: 248,570` 是 **torchsummary 数错了**：

- `sum(p.numel() for p in model.parameters())` = **242,365**（可训练权重+偏置）
- 加了 BN 的 `running_mean/running_var/num_batches_tracked`（**推理时可折进卷积，不该计入**）= 250,934
- torchsummary 的 248,570 = **242,365 + 6,205**

那 6,205 是 **LightFPN 里有 3 个带参数的模块在一次前向里被调用了两次**，
torchsummary 是按「每次 forward 调用记一遍」累加的，所以重复计了。
（已验证：`242365 + 6205 = 248570`，一次前向里调用次数 >1 的带参数模块恰好 3 个。）

⇒ **部署该按 242,365 算**：fp32 约 0.97 MB，int8 约 242 KB。
之前报告里写的 0.95 MB / 248,570 差得不多，但来源是错的，这里改过来。
